# Git Note History 第四轮产品头脑风暴

日期：2026-07-29

基线：v0.6.0

状态：研究与候选方向。本文不改变当前开发顺序；功能是否实现仍以 `ROADMAP.md` 的勾选状态为准。

## 这轮如何避免重复

第三轮已经覆盖命名里程碑、工作事件、知识版二分追踪、恢复篮子、历史沙盒、多来源历史、知识图谱时间机、来源可信度、版本批注和历史健康。

这一轮不再继续横向增加 Diff 模式，也不把已有方向换名重提，而是探索四个更远的问题：

1. 历史能否被查询、验证和引用，而不只是按时间浏览；
2. 笔记能否表达“兼容性、约束和事实有效期”；
3. 研究过程能否保留主张、证据、预注册和决策的演化；
4. 交付物、自动生成内容和敏感历史能否具备可审计的来源链。

## 新补充的研究依据

- [Git blame](https://git-scm.com/docs/git-blame)：`--reverse`、`-M` 和 `-C` 为内容消失、移动和复制追踪提供了原生基础。
- [Git log](https://git-scm.com/docs/git-log)：`-S` 和 `-G` 可按字符串数量或正则变化缩小历史搜救范围。
- [Git range-diff](https://git-scm.com/docs/git-range-diff)：比较两个 commit ranges，配对相似提交并展示 diff-of-diffs；其输出面向人阅读且可能变化，不能直接作为稳定机器格式。
- [Git bundle](https://git-scm.com/docs/git-bundle)：可以离线携带和验证一组 Git 对象与引用。
- [DataCite Versioning](https://support.datacite.org/docs/versioning)：区分重大与次要变化，并用明确关系连接资源版本。
- [W3C SHACL](https://www.w3.org/TR/shacl/)：为 RDF graph 定义约束并生成结构化验证报告；本项目只借鉴这种验证模式，除非未来明确引入 RDF 映射。
- [W3C PROV](https://www.w3.org/TR/prov-overview/)：用实体、活动、Agent、派生和修订表达可交换的来源信息，支持后续可信度与可复现性审查，但不保证内容可复现。
- [时间数据库综述](https://www.cs.arizona.edu/~rts/pubs/EDC.pdf)：区分 valid time 与 transaction time，为“记录于何时”和“声明适用于何时”提供模型依据。
- [Crossref Retraction Watch](https://www.crossref.org/documentation/retrieve-metadata/retraction-watch/)：可查询论文撤稿，以及覆盖较不完整的更正、关注声明和恢复发表记录。
- [OSF Registrations](https://help.osf.io/article/330-welcome-to-registrations)：预注册是数据收集或分析前形成的带时间戳只读研究计划。
- [AWS ADR process](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)：决策记录保留背景、决定和后果，新决策通过 `Superseded` 替代旧决策。
- [GitHub artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)：把生成物关联到源仓库、commit 和生成过程，但来源证明不等于内容正确。
- [GitHub sensitive-data removal](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)：敏感内容一旦进入历史，清理需要撤销凭据、重写历史并协调所有副本。
- [JetBrains Local History](https://www.jetbrains.com/help/webstorm/local-history.html)：内容搜索、删除恢复、标签和补丁导出说明历史也可以是检索与交接工具。

## 十个新方向

### 1. 历史查询引擎与消失内容搜救

不只搜索当前笔记的已有版本，而是让整个 Vault 的历史可以被结构化查询：

- “我曾在哪篇已删除笔记中写过 `predictive updating`？”
- “上个月之后，哪些笔记把 `status` 从 `pending` 改成了 `confirmed`？”
- “哪一版仍包含这段引用，后来移动到了哪里？”
- “在某个里程碑之前，哪些申请材料提到旧邮箱？”

第一版提供确定性的筛选器：时间、目录、路径状态、文本、属性变化、链接变化、作者和里程碑。自然语言只负责把问题翻译为可见的查询条件，最终执行条件必须允许用户检查。

它与 v0.5.3 的区别是范围从“当前笔记的已加载历史”扩展到“跨文件、已删除文件和结构化历史条件”。实现应先用 `git log -S/-G` 缩小候选，再读取内容确认；本地索引必须可选、可清除，并明确可能保存已删除的敏感文字。

**价值：高　惊喜度：中　难度：中到高**

---

### 2. 笔记语义版本与兼容契约

把笔记中的稳定标题、块 ID、Frontmatter 字段、查询输出和嵌入位置视为“知识接口”：

- `PATCH`：措辞、排版、拼写或引用格式修正；
- `MINOR`：增加新结论、新字段或向后兼容的内容；
- `MAJOR`：删除稳定块、改变字段含义、反转核心结论或破坏下游引用。

插件只建议级别并展示依据，由用户确认；不能因为改动行数多就自动判为重大版本。界面重点不是显示 `v2.3.1`，而是回答“哪些下游笔记、模板、嵌入和查询需要重新检查”。

`PATCH / MINOR / MAJOR` 是对 [Semantic Versioning](https://semver.org/) 的类比应用；只有用户声明的兼容契约未被破坏时才能建议 `MINOR`。新增结论并不天然向后兼容，DataCite 也允许资源维护者自行定义重大与次要变化。

它与命名里程碑不同：里程碑回答“哪一版在现实中重要”，语义版本回答“这一版是否仍与下游兼容”。

**价值：高　惊喜度：高　难度：中**

### 3. 知识单元测试与历史 CI

允许用户为 Vault 声明少量、可解释、只读的知识约束：

- `sent_final: true` 时不得同时出现 `evidence: pending`；
- 对外结论必须有来源链接；
- 在用户声明为唯一登记表的对象集合中，研究对象 ID、申请编号或 DOI 不得重复；
- 某个数值必须位于合理区间；
- 指定章节、属性或附件不得无提示消失；
- 结论变化时引用区必须进入复查状态；
- 恢复预演不得新增断链或破坏 YAML。

规则可以对工作区、任意 commit、工作事件或恢复预演运行，输出“通过 / 警告 / 失败”和具体事实，不输出无法解释的总分。结果可以直接进入首次失败版本。哪些块属于“结论”、哪些集合要求唯一，都必须由用户或明确模板声明，首版不能从任意正文自动猜测。

它比知识版二分追踪更系统：二分追踪定位一个已知问题；历史 CI 长期守护一组用户明确写下的契约。首版只支持声明式内置规则，不运行任意 shell 或 JavaScript，也不默认阻止写入。

**价值：很高　惊喜度：高　难度：中**

### 4. 主张—证据谱系与更正冲击

把普通链接进一步区分为“支持、反驳、限定、转述、数据来源和待核实”：

- 用户显式声明某句话由哪段原文、哪篇论文或哪个数据结果支持；
- 主张变了而显式关联的证据没变时，形成“需要复查”的启发式提示；
- 引用被更正、撤稿或替换时，列出受影响的笔记、段落、里程碑和交付物；
- 回答“发给导师的版本里是否使用了后来被撤回的论文”。

它与知识图谱时间机不同：图谱时间机追踪链接边是否变化；本方向追踪用户声明的证据语义，并提示支持关系是否需要重新审阅。插件不能判定一篇论文是否真正支持某句话。历史内容只能显示当时记录了什么，不能把当前的撤稿状态伪装成过去已经知道的事实。

Crossref 联网检查必须显式启用。Crossref 的撤稿数据覆盖最完整，更正、关注声明和恢复发表记录并不完整；查不到更新不代表论文当前、正确或适合作为证据。联网查询可能暴露研究兴趣；也应支持用户下载公开数据后完全本地检查。

**价值：很高　惊喜度：很高　难度：高**

### 5. 双时间知识史

Git 能观察到“什么时候以当前提交形式写进历史”，但 author time、committer time 都可能被错误时钟或历史改写影响，不是不可篡改的数据库事务时间。事实或主张还可以声明“适用于哪个现实时期”：

- 2026-07-29 才记录：某政策从 2026-04-01 起生效；
- 今天纠正去年的事实，不代表去年当时已经知道；
- 一项录取要求未来某日才开始适用。

插件提供两个时间镜头：

1. **记录时间**：在某个历史时点，Vault 当时写了什么；
2. **有效时间**：当前记录声明某个主张适用于哪个时期。

因此能区分两个问题：“当前可见 Git 历史显示，2025 年 10 月时 Vault 记录了什么？”与“当前记录认为，某个主张在 2025 年 10 月是否适用？”两者都不是对客观事实的自动证明。

有效时间必须由用户或明确元数据提供，不能根据正文自动猜测。首版只对显式标注的属性或块启用。

**价值：中到高　惊喜度：很高　难度：高**

---

### 6. 研究计划基线与预注册偏移雷达

把某个命名里程碑指定为“本地研究计划基线”，此后结构化比较：

- 假设、主要终点、排除规则、样本量、协变量和分析模型是否改变；
- 结果出现后是否新增分析；
- 改动属于预先声明的条件分支、正式修订、偏离还是探索性分析；
- 自动生成一份由用户最终分类的 deviation log。

只有连接 OSF registration 或其他可验证的不可变外部登记后，界面才可以称为“预注册偏移”；普通 Git commit 和本地里程碑都可能被改写，不能冒充正式预注册。“结果出现时间”也必须由用户声明，不能由插件猜测。

插件只报告“与计划基线不同”，不能自动使用“违规、可疑、不当”等裁决语言。合理的方法修正必须能够记录原因和新版本，而不是被当作错误。未公开假设和方案默认只保存在本机；联网、导出和分享前必须单独审查。

它把现有命名里程碑、结构化 Markdown 比较和历史批注组合成一个研究专用工作流，对实验设计、论文方法和博士项目尤其有辨识度。

**价值：高但人群集中　惊喜度：很高　难度：中**

### 7. 决策考古与替代链

很多版本能告诉用户“改了什么”，却没有保存“为什么选择 A、为什么放弃 B”。本方向建立轻量决策记录：

- 背景；
- 考虑过的选项；
- 选择与理由；
- 预期后果；
- 后续验证结果；
- `supersedes` 替代关系。

已接受决策不直接改写；新认识形成新的决策记录并替代旧记录。打开相关笔记、工作事件或恢复预演时，插件提示“这次变化受哪项决策约束”“恢复旧段落是否会重新引入已经被否定的方案”。

它与版本批注不同：批注讨论某个修改；决策记录表达领域层面的选择、理由和后果。

**价值：很高　惊喜度：高　难度：中**

### 8. 平行草稿竞技场

让用户比较两条写作路线，而不制造大量 `final-v2-really-final.md`：

- 假设 A 与假设 B；
- 简洁版与完整论证版；
- 给导师版与自用版；
- 两个 Agent 或两次人工改稿方案。

中央页不只比较最终文本，还显示两组修改如何对应：哪些修改被保留、改写、拆分、合并或放弃。已有真实 Git 分支时可借鉴 `git range-diff` 的 patch-series 配对思路，但不能解析其不稳定的人类可读输出；产品需要自建 patch-id、结构指纹和相似度模型。普通用户第一版可以使用本地只读 patch 车道，明确导出后才写文件，不自动创建或切换分支。

它与历史沙盒不同：沙盒在旧世界里试改；平行草稿竞技场管理面向未来、尚未决定采用哪条路线的多个方案。

**价值：高　惊喜度：很高　难度：高**

### 9. 可复核生成与交付胶囊

让 PDF、Word、图表、统计结果、转录摘要和自动生成段落都能追溯到来源：

- 输入文件与 hash；
- 源 commit、历史路径和固定段落锚点；
- 使用的脚本、工具、模型或模板版本；
- 参数或提示模板 hash；
- 输出文件 hash；
- 人工确认状态；
- 从生成到最终落盘发生的修改。

当输入变化后，插件提示“该交付物可能已过期”；点击已发送 PDF 可回到准确源版本，并显示之后发生了什么。需要交接时可导出 manifest，进阶用户可选择附带可检查对象和前置关系的 `git bundle`，但不自动上传或发送。

它比命名里程碑和来源可信度镜头更深：里程碑记录“已导出”，来源镜头记录“谁改的”，生成与交付胶囊回答“用哪些输入和过程产生了哪个具体文件”。来源证明不等于内容正确。

可信度必须分级显示：

1. **可追溯**：本地 manifest 记录输入、过程和输出，但清单本身仍可能被修改；
2. **完整性可检查**：受保护的 Git 对象、hash 或签名能发现内容漂移；
3. **有身份背书的来源证明**：签名或受信构建 attestation 还能验证声明者身份与生成环境。

GitHub artifact attestation 是 GitHub Actions 软件构建中的加密签名声明，不能直接等同于插件本地保存的 manifest；`git bundle verify` 也不证明作者身份或内容正确。默认只保存 hash、工具名和授权结果；原始提示、参数、输入正文、随机状态和私人路径必须逐项选择。缺少这些材料时只能称为可追溯，不能承诺非确定性生成能够逐字重放。

**价值：很高　惊喜度：很高　难度：中到高**

### 10. 历史隐私与泄漏考古

普通敏感信息检查只看当前文件，但 Git 历史可能永久保留已删除的：

- API key、token、密码和私钥；
- 邮箱、手机号、地址、证件号；
- 申请材料、财务数据、医疗或研究参与者信息；
- 不应进入公共仓库的附件。

插件只读扫描选定历史范围，显示首次出现、最后存在，以及对象在当前本地 refs、已 fetch 的 remote-tracking refs 或用户明确查询的远端中是否可达。它无法知道未 fetch 的远端、fork、其他 clone、缓存和历史下载副本，也不能提供“全网已删除”或合规证明。

处理顺序必须正确：先撤销或轮换凭据，再预演历史重写影响，最后由用户在外部工具中明确执行；插件首版不直接重写历史或强制推送。检测只能是 best-effort，必须承认误报和漏报。

检测结果本身高度敏感，只在本机显示，默认遮蔽内容并允许彻底清除索引。它不是一般健康检查，而是针对“已经进入历史的隐私”的专门取证与处置路线。

**价值：很高　惊喜度：中　难度：中到高**

## 推荐顺序

| 顺序 | 方向 | 先验证什么 |
| --- | --- | --- |
| 1 | 知识单元测试与历史 CI | 只读检查 YAML、来源、必备章节和断链，验证误报率 |
| 2 | 历史查询引擎 | 先支持当前目录、文本和属性变化，不先建全库常驻索引 |
| 3 | 决策考古与替代链 | 用 Markdown 轻量模板和 `supersedes` 做最小闭环 |
| 4 | 可复核生成与交付胶囊 | 先做源 commit、文件 hash、固定历史引用和导出后漂移提示 |
| 5 | 研究计划基线与预注册偏移雷达 | 先比较一个本地计划基线的结构字段，不冒充正式预注册 |
| 6 | 笔记语义版本 | 先由用户声明稳定字段和块，不自动推断全部知识接口 |
| 7 | 历史隐私与泄漏考古 | 先做离线规则、遮蔽结果和只读报告 |
| 8 | 主张—证据谱系 | 先支持显式关系，再接可选外部论文状态 |
| 9 | 双时间知识史 | 先支持明确 `valid_from` / `valid_to` 的属性 |
| 10 | 平行草稿竞技场 | 等恢复篮子和跨文件事件模型稳定后再研究 patch 车道 |

## 不作为新大方向、归入已有路线的好点子

- **冲突记忆**：复用过去人工解决方案，归入三栏冲突解决器继续增强；可借鉴 [Git rerere](https://git-scm.com/docs/git-rerere)，但再次应用前仍需预览和确认。
- **恢复演习**：在临时目录重建指定里程碑并核对附件、链接和对象完整性，归入历史健康中心。
- **可引用历史锚点**：固定到 commit、历史路径和块指纹，归入版本批注协议与生成交付胶囊。
- **“上次看过以后”蓝点**：归入现有复查 checkpoint，不建立第二套已读状态。
- **插件操作日志**：归入恢复安全中心现有回执与撤销栈，未来扩展到跨文件事务。
- **段落血缘与演化回放**：归入现有段落历史和时间旅行，不重复建设顶级入口。

## 设计底线

1. 新方向仍必须服务“发现、理解、验证、恢复或交付”，不能再次堆平级按钮。
2. 所有历史判断必须区分 Git 确定事实、用户声明和启发式推测。
3. 联网查询、原始提示、私人路径和敏感历史索引默认关闭或最小化保存。
4. 研究偏移、Agent 来源和撤稿状态只触发复查，不自动给内容或作者定性。
5. 规则检查必须展示使用的事实、条件和失败位置，不输出不可解释的神秘分数。
6. 任何会写文件、改分支、重写历史或发送内容的动作仍需独立预演与明确确认。
