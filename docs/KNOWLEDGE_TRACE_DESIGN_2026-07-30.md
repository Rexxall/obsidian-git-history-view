# 知识版二分追踪设计

日期：2026-07-30

目标版本：v0.6.2

状态：已完成并通过本地发布验收。实现范围与验收结果以 `ROADMAP.md` 和 `RELEASING.md` 为准。

## 要回答的问题

- 一句话从哪一版开始出现、消失或变成另一种写法？
- 一个 YAML 属性从哪一版开始满足或不再满足指定条件？
- 一个链接、嵌入或标签从哪一版开始存在或缺失？
- 一个确定性的 Markdown 结构或内容规则从哪一版开始通过或失败？
- 如果条件反复变化、版本不可读或工作区已改变，哪些结论仍然可信？

它不是普通关键词轨迹的换名版本。内容轨迹回答“出现和删除过几次”，知识追踪接受一个明确声明，区分候选边界、已确认边界、反复变化和未知间隙。

## 核心对象

### 版本序列

版本按 Git 第一父链从旧到新排列，使用 `--follow` 和 rename 路径连续性。作者时间只用于展示，不参与排序。

当前工作区可以作为最后一版，但必须在追踪开始时冻结正文与指纹。之后笔记变化只会使结果标记为过期，不会静默替换快照。

### 声明

首轮范围：

- 文本：包含、不包含、精确匹配，可选区分大小写；
- 属性：存在、缺失、等于、包含，保留 YAML 类型；
- 关系：Wikilink、Markdown 链接、嵌入和标签是否存在；
- 结构：标题、任务、代码块、Callout、表格和公式等确定性结构；
- 内置规则：只依赖单个版本正文、结果可解释、不执行任意代码；
- 人工判断：由用户明确标记成立、不成立或未知。

自动规则不得猜测“作者真正想表达什么”。人工结果也不得显示成自动验证。

### 三态结果

每个版本只有三种判定：

- `holds`：声明成立；
- `does-not-hold`：声明不成立；
- `unknown`：正文不可读、超限、解析失败，或人工选择无法判断。

`unknown` 不是失败，也不能被邻近版本填补。

## 边界算法

1. 先检查序列两端并按二分顺序探测，尽快得到候选边界。
2. 自动声明随后验证完整区间，检查候选是否被未知版本或重复转变推翻。
3. 只有全部版本可判断，并且状态恰好转变一次，才显示“已确认首次变化”。
4. 出现多次转变时显示完整转变列表，并明确称为“反复变化”。
5. 有未知版本时显示未知区间；不跨越未知区间断言具体 commit。
6. 全部状态相同称为“历史稳定”；全部未知称为“无法判断”。

界面必须把二分探测次数与最终验证版本数分开显示，避免让“候选”看起来像完整证明。

## 人工流程

人工模式一次突出一个待判断版本，并提供：

- 仍然成立；
- 已经变化；
- 无法判断。

二分可以缩小候选区间，但只有用户完成必要验证后才能升级结论。尚未完整验证时统一使用“人工候选”，不能显示“自动确认”。

## 读取与并发边界

- 不调用 `git bisect`，因为它会写入仓库状态；
- 不 checkout、不移动 HEAD、不创建分支、不修改索引；
- 只使用 `log`、`show`、`cat-file`、`rev-parse`、`status` 和 `diff --cached` 等读取命令；
- 对版本数、单文件大小、总读取量和并发读取数设上限；
- 工作区正文读取前后复核 HEAD、状态和内容指纹；
- Vault 内路径若物理落点位于 Vault 外，不读取正文；
- 快速重复发起采用 last-call-wins，关闭页面使旧任务失效。

## 界面结构

中央工作台分为四层：

1. 笔记身份、声明摘要、只读与工作区快照状态；
2. 结论卡：已确认、候选、反复变化、稳定或未知；
3. 边界两侧版本，可打开固定内容的现有只读对比；
4. 旧到新的紧凑状态时间线，按连续状态分组，需要时展开单版证据。

设置弹窗只收集声明，不展示结果。高级选项按声明类型出现，避免把全部规则堆在一个表单里。

## 非目标

v0.6.2 不做以下操作：

- 自动改写“错误”内容；
- 自动恢复到边界版本；
- 执行用户提供的 shell 或 JavaScript；
- 对整个 Vault 做长期后台扫描；
- 把作者时间当作 Git 拓扑顺序；
- 把缺失对象、浅克隆或损坏历史解释为声明失败。
