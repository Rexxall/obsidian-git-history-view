# Git Note History 第三轮产品头脑风暴

日期：2026-07-29

基线：v0.5.5

状态：研究与规划，以下方向均未实现。

## 这轮为什么要换方向

v0.5.5 已经完成单篇笔记的核心闭环：

> 发现待复查变化 → 理解内容与结构变化 → 安全恢复 → 保留可撤销记录

继续增加 Diff 模式、按钮或装饰的边际价值已经很低。下一阶段更值得探索的是三个问题：

1. 历史能不能回答“什么时候、为什么、由谁把知识变成了现在这样”；
2. 能不能从多个版本中安全重组内容，而不只是整篇回退；
3. 能不能把单篇文件历史扩展为工作事件、知识关系和可信来源的历史。

这意味着产品可以从“Git 版本查看器”继续成长为一个轻量的知识演化与恢复工作台，但仍需保持边界：不替代完整 Git 客户端，不默认联网，不自动提交、推送或移动 HEAD。

## 新补充的研究依据

- [VS Code Timeline 与 Local History](https://code.visualstudio.com/docs/editing/userinterface#_timeline-view)：Git 提交与本地保存可以共处一条时间线，但来源和保留策略必须明确；历史条目可比较、恢复、重命名和删除。
- [VS Code Source Control](https://code.visualstudio.com/docs/sourcecontrol/staging-commits)：从单行、修改块、文件到多文件 commit 逐层审阅，并提供统一 Diff、局部操作和多文件提交视图。
- [GitLens 2026 release notes](https://help.gitkraken.com/gitlens/gitlens-release-notes-current/)：补丁复制、Commit Composer、worktree 聚焦、Agent 活动和响应式工具栏说明“编排变化”和“区分工作上下文”正在成为新的历史交互重点。
- [Git worktree](https://git-scm.com/docs/git-worktree.html)：同一仓库可拥有隔离的工作目录，共享历史但保留独立 HEAD 和索引，适合作为安全历史沙盒的底层能力。
- [Git notes](https://git-scm.com/docs/git-notes)：可为 commit 附加说明而不改写 commit 本身，为可选的便携审阅批注提供了原生载体。
- [Git bisect](https://git-scm.com/docs/git-bisect)：二分查找不仅能找代码错误，也能寻找“某个性质从旧变新”的准确边界。
- [Google Docs 命名版本](https://support.google.com/docs/answer/190843)：命名版本把密集自动历史转成用户真正记得住的里程碑。
- [Overleaf History and versioning](https://docs.overleaf.com/writing-and-editing/history-and-versioning)：标签和版本区间比较适合论文、申请材料等长周期文档。
- [Notion Version history](https://www.notion.com/help/duplicate-delete-and-restore-content#version-history)：历史先显示内容和区块变化摘要，局部内容可复制，整页恢复仍保留后续历史。
- [Obsidian Sync Version history](https://help.obsidian.md/Obsidian%2BSync/Version%2Bhistory)：删除、重命名、附件和普通笔记历史拥有不同入口，跨来源历史不能伪装成同一种持久性。
- [GitHub blame 与忽略修订](https://docs.github.com/en/repositories/working-with-files/using-files/viewing-and-understanding-files)：追溯内容时可以跳过大规模格式化等低价值 revision，同时保留查看原始结果的入口。

## 十个新方向

### 1. 知识版二分追踪：从哪一版开始变错

**要回答的问题**

- 这个结论从哪一版开始写错？
- 这个链接从哪一版开始断？
- 这个属性什么时候从“待确认”变成了“已确认”？

**交互**

用户选中一句话、属性、任务、链接或一条校验规则，标记“这版还对”和“当前已错”。插件像 `git bisect` 一样每次只展示中间的一个版本，让用户选择“仍然正确 / 已经变化 / 无法判断”，快速缩小到准确边界。

整个过程只读取 `git show`，不 checkout、不移动 HEAD。对于可自动判断的条件，例如“链接是否存在”“属性是否等于某值”“是否含某句话”，可以自动完成二分。

**价值**

现有内容轨迹擅长回答“何时出现或删除”，二分追踪进一步回答“何时开始不正确”。它对研究结论、申请材料、配置笔记和长期任务都很有用。

**难度：中**

---

### 2. 命名里程碑与现实事件锚点

**要回答的问题**

- 哪一版是“发给导师的版本”？
- 哪一版是“提交申请时的版本”？
- 上次阅读、导出 PDF、发送或确认之后发生了什么？

**交互**

在版本上提供轻量动作“标记为里程碑”，常用类型包括：

- 已发送
- 已提交
- 已确认
- 已导出
- 重要草稿
- 自定义名称

时间线默认仍显示有效版本，但可一键切换为“只看里程碑”。比较菜单新增“与上次发送版 / 上次确认版比较”。锚点默认保存在插件本地，不修改笔记和 commit；未来可选同步到独立元数据文件或 Git notes。

**价值**

人通常不记得 hash，却记得“交给谁的那一版”。这是低认知负担、高复用率的入口，也能把已有的标签、复查点和版本状态收束成一个统一模型。

**难度：低到中**

---

### 3. 工作事件：从单篇历史扩展到“一次工作改了什么”

**要回答的问题**

- 我昨晚那次整理同时改了哪些笔记、附件和链接？
- 这篇笔记的变化是否只是更大一次项目调整的一部分？
- 恢复这一段时，是否还应该检查同一事件中的其他文件？

**交互**

点击版本旁的“查看本次工作事件”，在中央页显示：

- 同一 commit 修改的文件；
- 同一编辑会话内相邻自动备份涉及的文件；
- 新增、删除、重命名的笔记和附件；
- 这些文件之间新增或移除的链接；
- 当前笔记在整个事件中的位置。

默认只是只读审阅。后续可允许把多个文件的修改加入同一个恢复方案，但必须统一预演和一次性撤销。

**价值**

Git 的真实单位是 commit，知识工作的真实单位往往是“一次整理、一次申请修改、一次文献吸收”。它能补上单文件视角丢失的上下文。

**难度：中**

---

### 4. 恢复篮子：从多个版本拼出理想笔记

**要回答的问题**

- 我想要旧版的方法段、较新版的结论和当前版的属性，怎么组合？
- 能否先把多个历史片段收集好，再一次性写回？

**交互**

在段落、标题、属性、表格行或修改块旁增加“加入恢复篮子”。篮子像购物车：

1. 收集来自不同版本的内容；
2. 显示每一项将替换、插入还是删除什么；
3. 检测目标位置冲突、重复内容、断链和属性覆盖；
4. 生成最终 Markdown 预演；
5. 一次应用，并生成一条完整恢复回执。

可拖动调整插入位置，但不允许在没有最终预演时直接连续写回。

**价值**

这会让插件从“恢复过去”升级为“利用过去重建现在”，是最可能形成独特竞争力的方向之一。

**难度：高**

---

### 5. 历史沙盒：在不碰当前 Vault 的情况下试用旧世界

**要回答的问题**

- 如果回到两个月前，整套笔记、链接和附件是什么状态？
- 我能否在旧版上试着改，不影响当前工作区？

**交互**

用户选择一个 commit，创建临时只读“时间胶囊”；需要编辑时，再明确升级为隔离沙盒。可采用临时目录或 Git worktree：

- 在独立 Obsidian 窗口打开；
- 显示明显的“历史沙盒”身份；
- 当前 Vault 保持不变；
- 完成后可复制笔记、导出补丁或把选中内容送入恢复篮子；
- 关闭时选择保留、归档或删除沙盒。

**价值**

单文件 Diff 无法完整呈现旧版 Vault 的链接解析、嵌入、Canvas 和附件关系。历史沙盒能真正“走进过去”，尤其适合大规模重构或研究项目阶段回顾。

**难度：高，需严格处理 Vault 配置和临时目录**

---

### 6. 多来源历史总线：Git、工作区、本地保存和 Sync 各自可插拔

**要回答的问题**

- Git 尚未提交前的内容还能否找回？
- 同一时间附近为什么有 Git、File Recovery 和 Sync 三种版本？
- 某个版本还能保留多久，是否可靠？

**交互**

设计统一的 `HistorySourceAdapter`，每条历史都显示：

- 来源；
- 是否可验证；
- 保留期限；
- 是否会自动消失；
- 能否恢复、复制或仅查看。

时间线可以合并排序，但视觉上绝不抹平来源。默认只启用 Git；File Recovery、Sync 或自建快照必须由用户单独开启，接口不稳定时可随时降级而不影响核心历史。

**价值**

这是完整灾难恢复能力的基础，但重点不是“多抓一些快照”，而是让用户知道每一份历史来自哪里、可信到什么程度。

**难度：高，探索项**

---

### 7. 知识图谱时间机与恢复冲击波

**要回答的问题**

- 这次修改让哪些概念、反链、嵌入和附件关系发生了变化？
- 恢复旧版后，整个知识网络会怎样改变？

**交互**

从现有单篇链接影响继续扩展：

- 时间轴播放的是关系变化，不是全文；
- 只显示发生变化的节点和边；
- 可按链接、嵌入、标签、附件、脚注筛选；
- 点击节点回到对应笔记和版本；
- 恢复预演显示“冲击波”：新增多少断链、恢复多少旧关系、哪些目标已经不存在。

大图不是默认入口。普通恢复只显示一句风险摘要，需要时再打开局部关系时间机。

**价值**

这是 Obsidian 特有、通用 Git 客户端很难做好的一层，也能让“恢复一篇文件”变成对知识库后果有感知的操作。

**难度：中到高**

---

### 8. 人、Agent 与来源的可信度镜头

**要回答的问题**

- 哪些段落是人工修改，哪些来自 Agent 或自动化？
- Agent 修改后是否经过人工复查？
- 一条结论改了，但对应引用有没有同步变化？

**交互**

在不常驻干扰写作的前提下，提供临时可信度镜头：

- 按段落显示最近修改来源；
- 读取已有 `Agent`、`Authority`、`Send-Gate`、`Workflow-Status` trailer；
- 区分人工、自动备份、脚本、Agent 和来源未知；
- 标出“Agent 修改后尚未人工确认”的块；
- 结论变化但引用未变化时给出审阅提示；
- `Esc` 立即退出镜头。

不因为某段来自 Agent 就判定其错误；它只表达来源和审阅状态，不替代事实验证。

**价值**

当越来越多笔记由自动化和 Agent 共同维护时，“内容是什么”之外还必须知道“它怎么来的、谁确认过”。现有 trailer 解析已经提供了可靠起点。

**难度：中**

---

### 9. 不改 commit 的版本批注与审阅协议

**要回答的问题**

- 能否给某个版本或某个修改块留下注释？
- 能否把审阅意见交给另一个人或另一台机器，而不改原始 commit？

**交互**

第一阶段使用本地批注：

- 批注绑定 commit、文件历史路径和 Markdown 块指纹；
- 支持待处理、已解决、无需处理；
- 历史移动后尽量重新定位，失败时保留原始上下文；
- 可导出为 Markdown 审阅包。

第二阶段可选使用专用 Git notes ref 同步批注，不改写 commit，也不污染笔记正文。界面必须明确提示 Git notes 默认不一定随普通 push 同步，并提供可审查的同步配置。

**价值**

它为导师审阅、跨 Agent 交接和个人长期批注提供结构化协议，同时保持 Git 历史原样。

**难度：中**

---

### 10. 历史信噪比与健康中心

**要回答的问题**

- 哪些 commit 只是格式化、时间戳或自动生成内容？
- 当前历史是否因为浅克隆、LFS、损坏对象或未推送提交而不完整？
- 哪些可恢复版本其实只存在于这台机器？

**交互**

分成两个互补部分：

**信噪比规则**

- 忽略时间戳属性、属性排序、换行风格、批量格式化和指定生成字段；
- 支持 Vault 级规则预设；
- 可读取 `.git-blame-ignore-revs` 作为可选参考；
- 永远保留“查看原始 Git 结果”。

**历史健康**

- 显示浅克隆、读取上限、缺失对象、LFS 指针、仓库错误；
- 区分已推送、仅本地 commit、仅工作区和短期快照；
- 提醒“这个版本尚未存在于其他设备”，但不自动 push；
- 提供只读诊断和明确修复建议。

**价值**

它让用户既少看无意义变化，又不会因过度过滤产生“历史很完整”的错误安全感。

**难度：中**

## 推荐优先顺序

| 顺序 | 方向 | 原因 |
| --- | --- | --- |
| 1 | 命名里程碑与现实事件锚点 | 复用现有标签、复查点和比较入口，价值直观、风险低 |
| 2 | 工作事件 | 把单篇历史连接到真实工作上下文，同时不需要新增写操作 |
| 3 | 知识版二分追踪 | 直接建立在现有内容轨迹与历史读取上，形成鲜明能力 |
| 4 | 恢复篮子 | 技术复杂，但最能加强“安全恢复”这一核心优势 |
| 5 | 人、Agent 与来源可信度镜头 | 与现有 trailer 和本地审阅状态天然衔接 |
| 6 | 历史信噪比与健康中心 | 提高长期可靠性，减少自动备份和不完整历史造成的误判 |
| 7 | 知识图谱时间机 | Obsidian 差异化强，但应等跨文件工作事件模型稳定 |
| 8 | 版本批注与审阅协议 | 先本地、后可选 Git notes，避免过早引入同步复杂度 |
| 9 | 历史沙盒 | 价值很大，但 worktree、Vault 配置和生命周期管理成本高 |
| 10 | 多来源历史总线 | 作为适配器研究，不让私有或易变接口成为核心依赖 |

## 建议先做的四项

### A. 命名里程碑

先统一 `bookmark`、`reviewCheckpoint` 和现实事件锚点的数据模型，提供“只看里程碑”和“与上次发送版比较”。

### B. 工作事件

先做只读多文件 commit / 编辑会话摘要，不急着恢复多文件。验证它能否真正解释“一次工作做了什么”。

### C. 知识版二分追踪

先支持文本存在、属性值和链接状态三种可自动判断条件，再补人工“仍然正确 / 已经变化”流程。

### D. 恢复篮子

第一版只允许同一篇笔记的段落和属性，沿用现有恢复预演、并发保护和撤销回执；跨文件恢复等工作事件模型稳定后再做。

## 设计约束

1. 新能力必须进入“发现、理解、恢复”之一，不继续增加平级主模式。
2. 侧栏只负责入口和摘要；多文件、沙盒、图谱和恢复编排进入中央工作台。
3. 任何来源合并都必须显示来源、保留期限和可信边界。
4. 任何恢复编排都必须先生成最终 Markdown，再一次写回并产生回执。
5. Agent 来源只用于解释和排队，不作为内容正确性的替代判断。
6. Git notes、worktree、Sync 和 File Recovery 都是可选增强，不能破坏纯 Git 基础路径。
7. 任何自动过滤都必须可解释，并可一键查看原始 Git 结果。
