# Git Note History 第六轮产品头脑风暴

日期：2026-07-30

基线：v0.6.1 工作事件已实现，发布验收尚未闭环。

状态：研究与候选方向。本文不改变第三轮当前开发顺序；功能是否实现仍以 `ROADMAP.md` 的勾选状态为准。

## 这轮为什么继续换坐标系

前五轮已经覆盖文件历史、Markdown Diff、段落恢复、命名里程碑、工作事件、历史查询、知识图谱、恢复篮子、历史沙盒、多来源历史、知识 CI、证据谱系、发布集、继续工作胶囊、非 Markdown 历史、知识保鲜与跨 Vault 联邦。

如果继续围绕“再多一个 Diff、搜索或摘要按钮”扩展，产品会越来越重，却不会更有辨识度。这一轮改看十个此前没有成为主对象的问题：

1. 文件改名、合并或拆分之后，现实中的人物、概念和项目还是不是同一个对象；
2. 一段想法被复制到多篇笔记后，哪份是源头，哪些分支已经漂移；
3. 未完成任务从 Markdown 中消失时，它是完成、取消、转移还是误删；
4. 中文、日文和英文对应内容如何在源文变化后进入复核；
5. 长工作事件如何分段审阅、暂停并继续；
6. 多设备、分支或 Agent 是否正在修改同一知识块；
7. 如何把历史从一次性搜索升级为可保存、可比较的查询工作簿；
8. 如何把内部修改转成面向不同读者的知识变更说明；
9. 如何精确链接到一个历史版本、修改块或工作事件，并让其他插件安全调用；
10. 原始材料、完整提取、精华笔记和正式输出之间如何形成可回溯的晋级链。

## 新补充的研究依据

- [W3C PROV-O](https://www.w3.org/TR/prov-o/)：用 Entity、Activity、Agent 以及 revision、quotation、derivation、specialization 等关系表达对象、修改活动与来源谱系。
- [Git `git log`](https://git-scm.com/docs/git-log)：Git 可以按相似度识别文件重命名与复制；`--find-copies-harder` 的高成本也提醒我们，块级复制追踪必须按需运行、缓存并显示可信度。
- [Weblate translation workflows](https://docs.weblate.org/en/latest/workflows.html)：源字符串变化后，旧翻译可以进入 Needs rewriting，而不是被直接判断为错误；翻译、待复核与已批准应是不同状态。
- [GitHub reviewing proposed changes](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request)：逐文件标记 Viewed、自动折叠已看内容并用进度条保存审阅进度。
- [GitHub pull request reviews](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/about-pull-request-reviews)：评论、批准、要求修改是不同决策；版本发生实质变化后，旧批准可以失效并要求重新审阅。
- [GitHub code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)：按路径声明责任人，并在相关内容变化时请求正确的人复核。
- [Automerge changes and history](https://automerge.org/automerge-swift/documentation/automerge/changesandhistory/) 与 [Automerge conflicts](https://automerge.org/docs/reference/documents/conflicts/)：一个历史时点可以有多个并发 head；冲突中的非胜出值不必丢失，可以作为明确的替代项供界面处理。
- [Dolt version control](https://www.dolthub.com/docs/sql-reference/version-control/)：把日志、差异、冲突和历史暴露为可查询的数据，并支持保存查询，说明“查询历史”可以成为稳定工作对象，而不只是搜索框。
- [GitLens Core Features](https://help.gitkraken.com/gitlens/gitlens-features/)：丰富的 commit 搜索和指向比较、commit、文件与行的 Deep Links，为历史互操作提供成熟参照。
- [Obsidian URI](https://obsidian.md/help/Extending%2BObsidian/Obsidian%2BURI)：原生 URI 已能定位 Vault、文件、标题与块，插件可在此基础上增加版本和比较参数。
- [Linear issue status](https://linear.app/docs/configuring-workflows) 与 [archive and restore](https://linear.app/docs/delete-archive-issues)：完成、取消和重复是不同终态；归档与删除也需要可恢复、可解释的活动记录。
- [GitHub generated release notes](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)：自动汇总变化后仍应按类别组织、排除噪声并由人检查最终内容。

## 十个新方向

### 1. 稳定实体身份与合并 / 拆分谱系

Git 能追踪文件路径，但现实对象不等于文件。一个实验室可能改名，两个人可能同名，一篇“大总表”也可能拆成多个项目笔记。

插件允许用户为人物、实验室、项目、概念、数据集和研究问题建立稳定实体 ID，并显式记录：

- 别名与改名；
- 两个实体被确认是同一个对象；
- 一个实体被拆成多个更精确对象；
- 先前误认被纠正；
- 哪些文件、标题、块和历史版本曾表达这个实体。

首版只接受用户确认或明确属性，不根据文件名相似度自动合并。合并和拆分只改变本地身份映射，不改写旧 commit；历史界面始终能看到“当时如何称呼”和“现在如何解释”。

它与文件路径轨迹不同：路径轨迹回答某个文件去了哪里；实体谱系回答文件结构变化后，现实对象是否仍保持身份连续。

**价值：很高　惊喜度：高　难度：高**

---

### 2. 想法家谱：复制、分叉与陈旧副本探测

Markdown 内容经常被复制到申请材料、论文提纲、会议笔记和总结中。复制后两边独立修改，普通链接图和 Git blame 都无法回答：

- 这段话最初来自哪篇笔记；
- 哪次复制形成了当前分支；
- 源段落变化后，哪些副本仍停留在旧表述；
- 两个相似段落是共同来源、独立写出，还是仅仅碰巧相似。

插件为标题、段落、列表和属性建立内容指纹，在用户按需扫描时生成“可能派生自”关系。先支持完全相同或高可信的复制，再逐步加入移动、轻微改写和跨语言手工配对。

界面只使用“可能复制”“可能同源”“已由用户确认”等中性表述，不做抄袭判断。大 Vault 必须限定目录、时间范围与相似度，避免 `--find-copies-harder` 式的全量高成本扫描。

它与反链不同：反链依赖作者显式建立链接；想法家谱寻找未显式链接但实际发生过复制和分叉的内容来源。

**价值：很高　惊喜度：很高　难度：高**

---

### 3. 承诺账本：任务、约定与删除去向

任务历史不应只有“这行被删了”。对于未完成 checkbox、明确 deadline、发送约定和跟进承诺，插件可以区分：

- 已完成；
- 已取消，并有理由；
- 已转移到另一篇笔记或任务；
- 合并为重复项；
- 暂缓或归档；
- 从工作区消失，但没有可解释去向。

当未完成承诺被删除时，它进入本地“去向待确认”列表，而不是自动恢复或阻止保存。用户可以把它标记为完成、取消、转移、重复或误删，并跳回删除边界和恢复预演。

首版只识别 Markdown 任务和用户显式标记的承诺，不从普通自然语言中猜测义务，不发送提醒，也不把插件变成新的任务管理器。

它与内容生命周期搜索不同：生命周期搜索发现一句话何时消失；承诺账本要求为高责任内容保留明确终态。

**价值：很高　惊喜度：高　难度：中**

---

### 4. 多语言对齐与翻译漂移

中文、日文和英文版本不能只做逐行 Diff。用户可以显式配对整篇、标题或块，声明：

- 哪个版本是当前源文；
- 哪些块是对应翻译；
- 哪些术语必须使用固定译法；
- 哪个源版本已经被各语言版本复核。

源文发生实质变化后，对应译文进入“需要复核”，并显示改变的源块、上次确认的源 commit、现译文和术语差异。仅改空格、格式或用户声明的非语义字段时，可以保持确认状态。

第一版依赖手工块 ID、标题或配对关系，不使用模型自动批准语义等价。可选辅助只能提出候选，不得把“相似”冒充“已同步”。

它与普通双预览不同：双预览比较两个文件；翻译漂移维护源文与多个语言版本之间长期、可复核的同步关系。

**价值：很高　惊喜度：很高　难度：中到高**

---

### 5. 可中断的版本审阅会话

工作事件可能包含几十个文件和上百个修改块。插件应把一次审阅本身保存为对象：

- 已看、未看、需要再看；
- 评论、通过、要求修改；
- 当前进度和最后位置；
- 被折叠的已看文件；
- 哪些批注因新 commit 而过期；
- 哪些目录、实体或材料需要特定责任人复核。

用户可以暂停后继续，也可以从“自上次审阅后新增的变化”开始，而不是重新检查全部内容。批准只绑定到准确 commit 或工作事件；底层变化后必须显示为旧批准，不延续为当前批准。

首版完全本地，可导出 Markdown 审阅包但不依赖 GitHub。路径责任规则只负责建议审阅人，不自动发送、分配或阻止 Git 操作。

它与版本批注不同：批注记录某处意见；审阅会话组织一整次可暂停、可完成、可失效的检查过程。

**价值：很高　惊喜度：中　难度：中**

---

### 6. 修改碰撞雷达与多 Head 预演

真正的冲突出现前，插件先比较当前工作区与用户可访问的其他状态：

- 已 fetch 的远端分支；
- 其他 worktree；
- 本地 Agent 分支；
- 多来源历史总线提供的 Sync 或设备快照；
- 用户指定的另一个候选版本。

雷达按 YAML key、标题、块、任务和链接显示重叠修改，并区分：

- 修改不同对象，可以安全并存；
- 同一对象两边都变了，需要提前协调；
- 一边删除、一边修改；
- 两边产生不同新值，应保留两个候选。

第一版只读、按需运行，不持续监控别人的设备，不自动 fetch，不自动合并。它只能提示“潜在重叠”，不能承诺无提示就一定不会产生 Git 冲突。

它与三栏冲突解决器不同：三栏解决已经发生的冲突；碰撞雷达在写回或合并前展示共同祖先之后的重叠编辑。

**价值：高　惊喜度：很高　难度：高**

---

### 7. 历史查询工作簿与结果集 Diff

搜索框适合临时寻找内容，但复杂问题值得保存：

- 所有曾删除但没有恢复的未完成任务；
- 某属性一年内的所有取值和变更者；
- 某实体关联文件在两个里程碑之间的变化；
- 所有复制自某段落、但尚未复核的副本；
- 自上次发送后，哪些已批准块再次改变。

用户用可视化过滤器或轻量查询语法组合路径、时间、作者、结构类型、里程碑、实体、任务状态和关系变化。工作簿可以固定、重跑、比较两个时间点的结果集，并导出 Markdown 或 CSV。

第一版不嵌入任意 SQL，也不执行用户脚本。查询必须分页、可取消、显示历史读取深度，并明确“完整历史”还是“当前缓存范围”。

它与历史查询引擎不同：查询引擎提供搜索能力；查询工作簿把问题、范围、结果和两次运行之间的变化保存成可复用研究对象。

**价值：很高　惊喜度：高　难度：中到高**

---

### 8. 面向读者的知识变更日志

同一批内部修改，对不同读者意义不同。插件可以基于命名里程碑、工作事件、发布集和审阅状态生成草稿：

- “自上次发送给导师后改变了什么”；
- “本周研究假设、证据和待确认项有什么变化”；
- “申请材料中哪些事实、附件和语言版本已更新”；
- “共享 Wiki 中哪些内容需要读者重新查看”。

用户先选读者、基线和范围，插件只生成可验证的结构化事实：新增、删除、状态变化、链接变化、已确认或待复核。解释性结论由用户编辑；最终可保存成普通 Markdown 笔记并保留每条项目的历史深链接。

默认不自动发布、不发消息、不把改动行数等同于重要性。自动生成后仍需让用户删减、改写和确认。

它与项目发布集不同：发布集冻结“一套材料是什么”；知识变更日志解释这套材料相对某个读者上次见到的版本发生了什么。

**价值：很高　惊喜度：中　难度：中**

---

### 9. 历史深链接与能力安全 API

插件中的版本、比较、工作事件和修改块应该能被准确引用。新增稳定链接，例如：

- 打开指定 Vault 中某篇笔记的某个 commit；
- 打开两个版本的比较并定位到一个修改块；
- 打开一个工作事件中的特定文件；
- 打开某条版本批注、审阅会话或恢复预演。

链接由 Vault ID、仓库指纹、commit、历史路径、对象指纹和视图类型组成。无法解析时显示缺失原因和可用降级路径，而不是跳到当前同名文件。

同时提供受限 API：其他插件和本地工具可以读取历史元数据、执行有界查询并请求打开界面；恢复、写回、创建里程碑等动作只能生成待确认意图，必须回到可见界面由用户确认。

它与 Markdown 审阅包不同：审阅包携带一批内容；深链接和 API 提供稳定、最小、可组合的历史入口，让插件成为 Obsidian 的历史基础设施。

**价值：很高　惊喜度：高　难度：中**

---

### 10. 知识晋级流水线：原料、提取、精华与正式输出

很多知识不是在同一篇笔记里不断修改，而是经过多个文件和阶段：

1. 原始网页、邮件、PDF、截图或录音；
2. 完整提取；
3. 优化后的精华笔记；
4. 结构化主张、项目材料或正式输出；
5. 后续更正、替代或归档。

插件允许用户声明 `derived-from`、`promotes`、`supersedes`、`canonical` 和 `archived` 等轻量关系，并在时间线上展示每次晋级：

- 原始材料是否仍保留；
- 完整提取是否有对应精华；
- 正式输出使用了哪个源版本；
- 上游材料变化后，哪些下游产物尚未重新检查；
- 多个候选精华中哪一个被确认为当前标准版本。

第一版只维护关系和复查状态，不自动移动、删除或覆盖文件，也不把目录名称猜成工作流状态。跨 Vault 晋级必须经过用户显式配对，并尊重每个 Vault 的隐私边界。

它与主张—证据谱系不同：证据谱系回答结论由什么支持；晋级流水线回答材料如何从原料经过加工成为当前可用的知识和交付物。

**价值：很高　惊喜度：高　难度：中到高**

## 推荐优先顺序

| 顺序 | 方向 | 第一阶段验证 |
| --- | --- | --- |
| 1 | 可中断的版本审阅会话 | 对一个工作事件保存 Viewed、待复查、进度和最后位置；新 commit 后使旧审阅明确过期 |
| 2 | 历史深链接与能力安全 API | 支持笔记版本、双版本比较和工作事件三类只读 URI，并安全降级 |
| 3 | 承诺账本 | 发现被删除的未完成 Markdown 任务，并要求选择完成、取消、转移、重复或误删 |
| 4 | 想法家谱 | 在用户指定目录中识别高可信的相同段落复制和后续分叉 |
| 5 | 多语言对齐与翻译漂移 | 手工配对两个带块 ID 的语言版本，源块改变后进入复核 |
| 6 | 稳定实体身份谱系 | 支持显式 ID、别名、合并与拆分，不改写历史文件 |
| 7 | 知识变更日志 | 从两个里程碑生成可核对、可编辑、带深链接的读者视图 |
| 8 | 历史查询工作簿 | 保存一个结构化查询，并比较两次运行的结果集 |
| 9 | 知识晋级流水线 | 对原始材料、完整提取和精华笔记建立显式晋级链 |
| 10 | 修改碰撞雷达 | 比较当前工作区与一个指定 ref 的结构化重叠，不自动 fetch 或合并 |

## 建议优先验证的四项

### A. 可中断的版本审阅会话

它直接解决当前工作事件变大后的使用问题，可以复用已有文件分组、修改块、版本批注和复查状态，投入最小、日常收益最高。

### B. 历史深链接与能力安全 API

先建立稳定历史地址，后面的审阅包、跨 Vault、查询工作簿、知识变更日志和 Agent 协作才不会各自发明一套不可互通的定位方式。

### C. 承诺账本

这是从“查看变化”迈向“防止重要责任悄悄消失”的明确价值点，而且首版只依赖现有 Markdown 任务解析和删除边界。

### D. 想法家谱

这是最有产品辨识度的一项：它让 Git Note History 不只知道文件怎么变，还知道想法如何被复制、分叉和遗忘。首版限定高可信精确复制，能控制误判与性能。

## 不作为本轮新大方向的相邻点子

- 编辑器行内年龄热力图、弹性上下文 Diff、窄屏主从布局和键盘导航，继续归入现有视觉与交互路线。
- 自动总结 commit、生成提交说明和模型语义搜索，继续归入可选辅助能力，不能成为上述功能的必需条件。
- 审阅评论、Git notes 与 Markdown 审阅包仍归入第三轮版本批注协议；本轮审阅会话只补充过程、进度和失效规则。
- 跨 Vault 实体映射由第五轮联邦提供边界；本轮实体谱系只定义对象身份和合并 / 拆分语义。
- 历史查询工作簿复用第四轮查询引擎，不另外建立常驻全文副本。
- 修改碰撞雷达不替代 Git merge，也不引入实时协作编辑器或新的同步协议。

## 设计底线

1. 任何推断都显示依据、范围与可信度；用户确认与算法候选必须可区分。
2. 查询、相似度扫描和碰撞分析必须按需运行、可取消、可分页，并限制历史深度与文件范围。
3. 历史链接包含 Vault 和仓库身份；解析失败不能回退到可能错误的同名文件。
4. 审阅、批准、翻译同步和实体合并只绑定准确版本，内容变化后不得偷偷沿用。
5. 恢复或写回仍需预演、并发检查、回执与撤销；API 不能绕过可见确认。
6. 原始材料、取消任务、旧译文和复制分支不得因“整理”被自动删除。
7. 默认本地优先，不自动 fetch、上传、发送、发布、commit、stage、push 或改写 Git 历史。
