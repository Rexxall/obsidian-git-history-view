# Git Note History 第五轮产品头脑风暴

日期：2026-07-29

基线：v0.6.1 工作事件已实现，发布验收尚未闭环。

状态：研究与候选方向。本文不改变第三轮当前开发顺序；功能是否实现仍以 `ROADMAP.md` 的勾选状态为准。

## 这轮解决什么空白

前四轮已经覆盖版本浏览、Markdown Diff、段落历史、安全恢复、复查收件箱、命名里程碑、工作事件、知识二分、恢复篮子、历史沙盒、多来源历史、图谱时间机、来源可信度、历史查询、知识 CI、证据谱系、决策记录、研究计划、交付胶囊与隐私取证。

这一轮不把旧能力换名重提，而是探索十个仍然空缺的对象和场景：

1. Git 历史自身被改写后，如何解释“历史发生了什么”；
2. 如何把一整套材料，而不是单个文件或 commit，当成版本对象；
3. 如何恢复中断前的工作上下文，而不只是恢复文件内容；
4. 如何在当前笔记中安全引用一个固定历史片段；
5. 如何解释 Bases 等派生视图为什么变化；
6. 如何理解 Canvas、图片、PDF 和表格内部的变化；
7. 如何在编辑前声明意图，并在编辑后验收实际结果；
8. 如何管理知识的复核期限，而不把“过期”误判为“错误”；
9. 如何安全执行会影响全 Vault 的结构迁移；
10. 如何在不合并仓库的前提下连接多个 Vault 的历史。

## 新补充的研究依据

- [Jujutsu operation log](https://docs.jj-vcs.dev/latest/operation-log/)：记录整个仓库每次操作后的视图，可检查、撤销或恢复到旧操作状态。
- [Jujutsu for Git experts](https://docs.jj-vcs.dev/latest/git-experts/)：区分仓库操作历史与单个 change 的 evolution log，为“历史的历史”提供了更清晰的产品模型。
- [Git reflog](https://git-scm.com/docs/git-reflog.html)：记录本地引用尖端的移动，可定位 branch switch、reset 等操作前的引用位置，但会过期且不是可共享的完整审计日志。
- [Git fsck](https://git-scm.com/docs/git-fsck)：可发现仍存在但不可达的对象；对象可能被垃圾回收，因此不能承诺永久找回。
- [Obsidian Workspaces](https://obsidian.md/help/plugins/workspaces)：原生保存打开的文件、标签页与侧栏布局，说明“工作状态”可以成为独立于文件内容的恢复对象。
- [GitHub permanent links](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)：用 commit ID 固定文件或行范围，避免分支继续移动后链接内容变化。
- [Obsidian internal links](https://obsidian.md/help/links) 与 [Obsidian URI](https://obsidian.md/help/uri)：支持标题、块与跨 Vault 导航，为版本钉选与历史深链接提供原生入口。
- [Obsidian Bases syntax](https://obsidian.md/help/bases/syntax)：Bases 的结果由查询定义、当前文件上下文、属性、链接和时间函数共同决定，适合做确定性的历史重放与因果拆解。
- [GitHub non-code file diffs](https://docs.github.com/en/repositories/working-with-files/using-files/working-with-non-code-files)：图片可用双图、滑杆和洋葱皮比较，CSV、PDF 与渲染文档也有专门视图。
- [Obsidian Canvas](https://obsidian.md/help/plugins/canvas)：Canvas 使用开放的 JSON Canvas 格式，节点、边和分组可以进行结构化比较。
- [Notion wiki verification](https://www.notion.com/help/guides/build-a-docs-first-culture-with-a-beautiful-team-wiki-powered-by-a-database)：页面验证可设置到期日，到期后提醒重新复核，而不是直接宣判内容错误。
- [RO-Crate](https://www.researchobject.org/ro-crate/specification/1.3/introduction.html) 与 [BagIt RFC 8493](https://www.rfc-editor.org/info/rfc8493/)：分别提供多文件研究对象描述与带 checksum 的可靠文件集合思路。本插件只能借鉴轻量 manifest；未完全实现规范时不得自称 RO-Crate 或 BagIt。
- [Obsidian Properties view](https://obsidian.md/help/Plugins/Properties%2Bview)：Obsidian 已支持全局重命名属性，历史插件可以进一步补足影响预演、事务撤销和历史连续性。

## 十个新方向

### 1. 历史的历史：操作飞行记录仪与丢失版本救生艇

普通时间线回答“笔记内容怎么变了”，但不能清楚回答：

- 为什么昨天可见的一段 commit 今天消失了；
- 某次 reset、rebase、branch switch 或自动化操作把 HEAD 移到了哪里；
- 插件刚才的恢复、撤销或批量操作实际改变了什么；
- 一个已删除分支中的内容是否仍可从本机找回。

新增第二条明确区分的时间线：

1. **内容历史**：commit 和工作区中的笔记变化；
2. **仓库操作历史**：引用移动、分支切换、历史改写以及插件自身的写操作回执。

首版只读取 `reflog`、可达性和插件已有恢复回执，显示操作前后位置、涉及引用、可找回期限与风险。发现 orphan commit 时只能先预览、固定临时保护引用或导出内容；不得直接 reset、rebase 或改分支。

Jujutsu 的 operation log 能保存整个仓库视图，Git reflog 只能提供本地、按引用记录且可能过期的线索。界面必须明确这种能力差异，不能把 Git reflog 包装成永久、完整或跨设备审计。

它与历史健康中心的区别是：健康中心检查历史是否完整、可读和已备份；操作飞行记录仪解释仓库状态如何从 A 变成 B，并协助找回刚刚失去可达性的版本。

**价值：很高　惊喜度：很高　难度：中到高**

---

### 2. 项目发布集：把“一整套材料”当成版本对象

单篇笔记里程碑不足以表达真实交付，例如一次博士申请、论文投稿或研究汇报通常同时包含：

- 主文档；
- CV、研究计划与附件；
- Canvas 或索引页；
- 导出的 PDF / Word；
- 模板、表格和引用清单。

用户可以建立一个命名发布集，例如“Chao 申请材料 · 发送版”，显式选择成员并冻结：

- 每个成员的 Vault、历史路径、commit、文件 hash 与角色；
- 必需成员、可选成员和缺失成员；
- 两个发布集之间新增、删除、替换和内容变化；
- 当前工作区相对该发布集已经漂移的项目；
- 可选的只读 manifest 与完整性校验。

第一版只保存本地 manifest，不复制文件、不自动打 tag、不上传、不发送。导出功能必须先展示成员和敏感信息清单。只有真正生成符合相应规范的包时，才可称为 RO-Crate 或 BagIt；普通发布集应使用自己的中性名称。

它与命名里程碑的区别是里程碑标记某个文件版本的重要性；与交付胶囊的区别是交付胶囊追踪某个生成物如何产生；发布集定义的是“一组材料本身就是一个可比较的版本对象”。

**价值：很高　惊喜度：高　难度：中**

### 3. 继续工作胶囊：恢复“上次做到哪”，而不只恢复文件

用户中断工作后，真正丢失的往往不是文件，而是上下文：

- 当时打开了哪些笔记和比较页；
- 正在看哪个版本、修改块或工作事件；
- 哪些问题还没解决；
- 哪个里程碑是当前可信基线；
- 下一步准备做什么。

继续工作胶囊在用户明确暂停时保存：

- 当前 Workspaces 布局引用；
- 打开的文件、聚焦段落和历史选择；
- 未完成的复查、恢复篮子或验收合同；
- 一句用户填写的“停在这里 / 下一步”；
- 创建胶囊时的 HEAD 与当前工作区摘要。

重新打开后先显示“胶囊创建以来发生了什么”，再由用户选择恢复全部布局、只打开相关文件或仅查看清单。段落定位失败时退回标题、文件或原始上下文，不偷偷跳到相似但不确定的位置。

默认只保存路径、稳定锚点和状态，不复制笔记正文到插件数据。它与工作事件不同：工作事件回顾一次已经发生的修改；继续工作胶囊保存一次尚未完成的思路与界面状态。

**价值：很高　惊喜度：高　难度：低到中**

### 4. 历史钉选嵌入：实时、冻结和变更提醒三种引用

Obsidian 的普通嵌入始终跟随当前内容，但研究与交付有时需要保留“当时看到的原文”。插件可提供三种明确模式：

- **实时**：继续显示当前块；
- **冻结**：固定到 commit、历史路径与块指纹；
- **提醒**：显示当前块，但来源变化后出现“需要复查”徽章。

用户可以从历史预览中复制一个版本钉选，或显式插入只读历史嵌入。嵌入顶部显示来源时间、里程碑、是否仍可解析，以及“与当前比较”。冻结内容不能伪装成当前内容，历史对象缺失时保留引用元数据与清楚的降级状态。

第一版只支持整篇、标题和显式块 ID；对普通段落只生成带可信度的内容指纹，不承诺永久定位。插入嵌入会修改当前笔记，因此必须预览实际写入的最小标记。跨设备使用前还要检查目标 clone 是否具有对应对象。

它与版本批注不同：批注对历史版本发表评论；版本钉选让准确的历史内容成为当前知识库中可阅读、可比较但不可误认的对象。

**价值：高　惊喜度：很高　难度：中**

### 5. 派生视图因果解释器：让 Bases 也能时间旅行

一张 Bases 表或统计摘要变化时，用户通常只看到结果变了，却不知道原因：

- 查询定义改了；
- 某些源笔记的属性改了；
- 文件改名或移出目录；
- 链接关系改变；
- 当前上下文或时间函数改变；
- 输入文件在那个历史时点尚不存在。

插件可以在两个 commit 上重放受支持的确定性视图，并把结果变化拆成：

1. 查询定义变化；
2. 候选文件集合变化；
3. 属性或链接值变化；
4. 排序、分组或显示配置变化；
5. 无法在历史环境中稳定重放的动态因素。

第一版只支持 Obsidian Bases 的一个明确子集：文件、路径、标签、属性、链接、布尔筛选和稳定排序。`today()`、`now()` 应允许选择“按历史时点”或“按当前时点”并明确标注。不得运行任意 Dataview JavaScript、模板脚本或第三方插件代码。

它与历史查询引擎不同：查询引擎在历史中寻找事实；因果解释器拿一个已经存在的派生视图，回答“结果为什么从这张表变成那张表”。

**价值：很高　惊喜度：很高　难度：高**

### 6. 非 Markdown 语义历史：Canvas、图片、PDF 与数据表

附件不应该永远只显示“二进制文件发生变化”。为不同文件类型提供可插拔的只读比较器：

- **图片**：双图、滑杆、洋葱皮、尺寸与文件大小变化；
- **JSON Canvas**：节点、边、分组、位置、颜色和引用目标变化；
- **CSV / TSV**：行列、主键和单元格变化；
- **PDF**：页数、页面缩略图和可提取文本变化；
- **音频**：时长、波形概览与用户已有转录锚点变化，后续再评估。

中央页仍采用统一的版本选择和变化导航，不给每种格式再造一套顶级入口。Canvas 可以额外提供“版本实验板”：把两个版本的变化节点放到临时空间中检查，但默认不写 `.canvas` 文件。

第一阶段最适合先做图片与 JSON Canvas：格式明确、视觉收益高、无需联网。PDF 文本提取、OCR 和音频转录都可能泄露内容或消耗大量资源，必须按需启用并限制文件大小。

它与现有附件列表的区别是从“知道文件变了”升级为“知道文件内部什么对象变了”。

**价值：很高　惊喜度：高　难度：中到高**

### 7. 变更意图与验收合同：编辑前说清目标，编辑后核对结果

开始一次大改时，用户可以用一分钟建立“编辑任务”：

- 目标是什么；
- 允许修改哪些文件或目录；
- 哪些标题、属性、链接和附件必须保留；
- 预期新增、删除或导出的内容；
- 完成后要达到哪些可检查条件。

任务结束时，插件把合同与真实工作事件对照：

- 实际修改是否超出声明范围；
- 必须保留的结构是否丢失；
- 预计修改是否遗漏；
- 是否产生未预期的附件、断链或配置改动；
- 哪些偏差已经由用户解释和接受。

首版由用户手动开始、暂停和结束，只使用确定性条件，不持续监控键盘，也不自动阻止保存。偏差只表示“计划与实际不同”，不能自动判断错误或不当。

它与决策考古不同：决策考古保存为何选择某个方案；与研究预注册基线不同：本方向适用于任意整理、写作、迁移或交付任务，是轻量的事前范围与事后验收闭环。

**价值：高　惊喜度：高　难度：中**

### 8. 知识保鲜：验证到期、责任人与依赖变化

“很久没改”不一定过时，“刚改过”也不一定可靠。用户应能显式声明：

- 谁负责复核；
- 哪个 commit 已被确认；
- 确认有效到什么时候；
- 哪些来源、属性或相关笔记变化后必须重审；
- 哪些内容是长期稳定、无需定期提醒。

状态只使用中性语言：

- 已确认至某日；
- 已到复核时间；
- 确认后来源发生变化；
- 依赖变化，尚未重新确认；
- 从未确认。

验证徽章绑定到准确 commit。只改格式或无关字段时可继续有效，但规则必须可见；依赖变化默认进入复查而不是直接撤销结论。到期只表示需要检查，绝不表示内容已经错误。

它与复查收件箱不同：收件箱主要回答“上次确认后哪些内容被改了”；知识保鲜还处理没有直接编辑但时间已到、来源已变或责任人需要重新确认的情况。它与历史 CI 的区别是 CI 检查声明式规则，知识保鲜管理人的确认期限与依赖关系。

**价值：很高　惊喜度：中　难度：中**

---

### 9. 历史感知批量重构工作室

知识库长期维护常见的高风险操作包括：

- Frontmatter 字段重命名或类型迁移；
- 标签体系合并与拆分；
- 标题、块 ID、附件和目录重命名；
- Wikilink、Markdown 链接、嵌入与 Bases 查询同步更新；
- 旧模板迁移到新结构。

工作室先建立一份迁移方案，再提供：

1. 全 Vault 影响清单；
2. 修改前后结构化预览；
3. 查询、模板、链接和嵌入兼容性检查；
4. 被跳过或无法确定的对象；
5. 一次性写入、完整恢复回执和事务撤销；
6. 路径、属性和实体的迁移映射，让后续历史追踪仍能解释改名前后关系。

第一版只提供少量确定性的内置变换，不执行任意脚本或未经预览的正则替换。应用前重新检查工作区，任何并发修改都应停止并要求刷新预演；插件不自动 commit、stage 或 push。

它与语义版本不同：语义版本诊断兼容性；与恢复篮子不同：恢复篮子利用过去重建当前内容；重构工作室负责有计划地执行未来的多文件结构迁移。

**价值：很高　惊喜度：高　难度：高**

---

### 10. 跨 Vault 历史联邦

Projects、the second test vault、PhD Vaults 或其他仓库有时描述同一项目、人物和交付物，但不能为了方便而合并：

- 每个 Vault 有不同隐私边界和 Git 远端；
- 同名文件不一定是同一对象；
- 某些材料只能在一个 Vault 中存在；
- 恢复操作不能跨边界偷偷写入。

插件允许用户显式登记少量 Vault 与项目映射，建立本地只读联邦索引：

- 从当前项目跳到另一个 Vault 的对应笔记或发布集；
- 比较两个 Vault 中用户明确配对的版本对象；
- 查看共享实体的别名、来源 Vault 与最后确认时间；
- 生成带 Vault ID、commit、历史路径和块锚点的受限深链接；
- 缺少权限或未挂载时只显示不可用，不缓存正文。

第一版不自动扫描整台电脑，不根据同名文件自动合并身份，不提供跨 Vault 恢复，也不把私人 Vault 的路径或内容写入另一个仓库。所有配对都由用户确认，索引可查看、清除和重新建立。

它与多来源历史总线不同：多来源总线解决同一文件的 Git、工作区、Sync 和 File Recovery 版本；跨 Vault 联邦解决多个独立知识空间之间的历史关联。

**价值：很高　惊喜度：很高　难度：很高**

## 推荐顺序

| 顺序 | 方向 | 第一阶段验证 |
| --- | --- | --- |
| 1 | 继续工作胶囊 | 保存并恢复一组文件、历史选择、未完成事项和一句下一步 |
| 2 | 项目发布集 | 建立本地多文件 manifest，比较两个发布集并检测当前漂移 |
| 3 | 历史钉选嵌入 | 支持整篇、标题和显式块 ID 的冻结引用与当前比较 |
| 4 | 非 Markdown 语义历史 | 先做图片滑杆 / 洋葱皮与 JSON Canvas 节点边比较 |
| 5 | 知识保鲜 | 对准确 commit 设置复核到期日，并在依赖变化后进入复查 |
| 6 | 变更意图与验收合同 | 对一个手动工作会话检查允许范围与必须保留项 |
| 7 | 派生视图因果解释器 | 重放 Bases 的确定性子集并解释结果集差异 |
| 8 | 操作飞行记录仪 | 只读展示 reflog、插件回执和可找回对象，不提供 reset |
| 9 | 历史感知批量重构 | 从属性重命名开始，完成预演、事务写入和撤销 |
| 10 | 跨 Vault 历史联邦 | 只支持用户显式配对的两个 Vault 和只读深链接 |

## 建议优先验证的四项

### A. 继续工作胶囊

最容易形成日常使用习惯，而且可以直接复用现有 Workspaces、工作事件、复查状态和版本选择。

### B. 项目发布集

它解决单文件历史无法表达“一套申请材料 / 一次投稿”的真实问题，也为未来交付胶囊和跨 Vault 比较提供稳定对象。

### C. 历史钉选嵌入

这是 Obsidian 原生感最强的新能力：历史不再只是一个查看页面，而能成为当前笔记中明确标注的固定引用。

### D. 图片与 Canvas 语义历史

先补齐最明显的非 Markdown 缺口；图片比较与 JSON Canvas 都可以本地、确定性地实现，不需要先引入 OCR 或外部服务。

## 不作为本轮新方向的相邻点子

- 稳定 change 身份与 rebase 后批注迁移，作为“操作飞行记录仪”和现有版本批注协议的底层能力。
- 冲突形成前的块级重叠提示，作为“变更意图与验收合同”和现有冲突解决器的后续增强。
- Canvas 版历史故事板，作为“非 Markdown 语义历史”的可选展示，不另建顶级入口。
- 跨插件历史 API 与深链接协议，作为“历史钉选嵌入”和“跨 Vault 历史联邦”的基础设施。
- 消失想法主动推荐，归入已有历史查询引擎；默认不建立常驻向量索引。
- 版本审阅进度、弹性上下文 Diff 和活动地图，继续归入现有复查、Diff 与工作区控制面板路线。

## 设计底线

1. 不把 reflog、文件 hash 或本地 manifest 夸大为永久审计、作者身份或内容正确性的证明。
2. 所有跨文件、跨格式和跨 Vault 功能先只读；真正写入必须独立预演、重检并可撤销。
3. 历史嵌入必须始终显示其来源版本，不能在视觉上伪装成当前事实。
4. Bases 重放只执行受支持的确定性表达式，不运行第三方脚本或历史插件代码。
5. 到期、偏差、来源变化和自动检测只触发复查，不自动给内容或作者定性。
6. 本地联邦索引、工作胶囊和发布集 manifest 均可查看、清除和迁移；默认不复制笔记正文。
7. 新能力必须进入现有侧栏、中央工作台或恢复安全流程，不再堆一排平级模式按钮。
